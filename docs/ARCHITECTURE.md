# Architecture

> Draft. This describes the intended design; it will change as the prototype teaches us things.

## Design goal

An AI agent should be able to perform a drone piece live, even though every decision it makes takes seconds. The architecture solves this by splitting **intent** (slow, from the agent) from **execution** (fast, in the engine).

### moodscore-dsp

The sound itself, written in Faust (`dsp/*.dsp`) and compiled to Rust at build time. It exposes a flat set of named parameters (cutoffs, levels, detune amounts, effect sends…). It knows nothing about moods, gestures or agents.

Today's graph: six drone voices (`drone_1` … `drone_6`), each two detuned sawtooths with their own slow random pitch drift; `drone_1` also carries a sub sine an octave below. Each voice has its own pitch, level, detune and drift. Each voice's two oscillators open slightly either side of the voice's position (width without delaying either channel); the two voices that sound at rest sit in the centre and the others come in mirrored pairs. The voices are summed with a gentle energy-based normalisation so a full chord grows a few dB rather than slamming the clipper, then go through a stereo Moog-style ladder low-pass, a stereo reverb, a mono-bass crossover (below 150 Hz both channels carry the same signal: the reverb summed with the dry signal would otherwise tip the bass to one side), the master gain and a `tanh` soft clip. Tests check that the image stays centred and that neither channel is delayed. At rest only `drone_1` (A1) and a quiet `drone_2` (E2) sound; the others wait at level 0 on A2, C3, E3, A3.

Faust is used because its standard libraries already provide virtual-analog filters, saturation, oscillators and reverbs, and because Faust code is compact enough to iterate on quickly.

Build integration: a small `build.rs` calls `faust -lang rust` directly (the `faust-build` crate lags behind the compiler; Faust 2.88 changed the shape of its Rust output). Rust code generated by Faust is committed under `crates/moodscore-dsp/generated/`, so the project builds without Faust installed. The build fails if the generated code would take a lock inside `compute()`, which Faust does for lookup tables such as `rdtable` or `os.osc`.

### moodscore-engine

Owns the audio callback. Targets cross from the control thread as one atomic per parameter (last value wins, which is exactly right for targets). Every 32 frames the audio thread:

1. Reads the targets.
2. Smooths every parameter toward its target (30 ms time constant; in the log domain for frequencies), so no change reaches the DSP as a step.
3. Runs the DSP.
4. Updates the level meters (peak, 300 ms RMS) for `get_state`. Richer analysis for `listen` comes in Phase 4.

A 1.5 s fade-in avoids a thump when the engine starts.

### moodscore-director

Where musical intent becomes motion.

- **Mood macros.** Six expressive dimensions, each in `0.0–1.0`:
  `tension`, `darkness`, `density`, `motion`, `distance`, `instability`.
  Each macro maps to many DSP parameters through curves defined in data, not code, so they can be tuned by ear without recompiling. A target can name many parameters with a `*` pattern (`drone_*/drift`).
- **Gestures.** A gesture is a trajectory: a target, a duration, a curve and an optional start offset. Gestures on different parameters run concurrently. A new gesture on a parameter that is already moving starts from wherever that parameter is right now, so changes of mind never cause jumps.
- **Scenes.** Named snapshots of the macro state and selected raw parameters, stored as JSON.

Runs on a control thread at 500 Hz and writes parameter targets to the engine.

Ownership: every parameter is under either macro control or manual control. Under macro control, at most one macro *sets* it (`"mode": "set"`, the default) and any number of macros *add* an offset on top (`"mode": "add"`); the sum is clamped to the parameter's range. With no setter, offsets start from the parameter's default. `gesture` takes a parameter into manual control starting from its current value, and it stays there: a hand-set value is a deliberate choice, so later morphs leave it alone (the state names the macros holding off under `held_from`). A `morph` with `reclaim` takes it back, blending from the manual value to the macros' value over the morph's duration.

The conductor also holds transport fades scheduled with `start_in`, and fires them from the control loop when due.

Harmony (`harmony.rs`) is pure music theory: keys and modes, Roman-numeral chords spelled by letter, and voice leading (each voice takes the chord tone that moves it least, covering the chord and avoiding unisons). The director walks a harmonic plan in its own clock: each chord change is anchored to the moment it was due (not the control tick that noticed it) and played as glides on the voice pitches. Voice pitches have a third owner, `harmony`, alongside macros and manual.

### moodscore-mcp

The MCP server, built on `rmcp`. It validates tool calls, turns them into director commands and reports state back. See [MCP_TOOLS.md](MCP_TOOLS.md).

### moodscore (binary)

Wires everything together: device selection, config, logging, and later a minimal GUI showing the macros moving so the human can watch, and intervene in, what the agent is doing.

## Real-time rules

The audio thread must never:

- allocate or free memory
- take a lock
- do I/O (files, network, logging)
- wait on another thread

All communication with the audio thread goes through preallocated lock-free queues (`ringbuf` or equivalent). These rules are not negotiable; a drone engine that clicks is useless.

## The latency model

| What | Timescale |
|---|---|
| Agent decides and calls a tool | 1–10 s |
| Director schedules a gesture | < 1 ms |
| Parameter reaches the audio thread | 1 audio block |
| Gesture plays out | seconds to minutes |

Because gestures are long compared with the agent's thinking time, the agent is always *ahead* of the sound, never chasing it. That is the whole point.

## Open questions

- Fixed DSP graph vs. switchable voice types per slot.
- How much the human can override the agent in real time, and how the agent learns about it (likely: the director records human changes and `get_state` reports them).
- Faust static compilation only, or optional JIT hot-reload (LLVM) for live DSP editing later.
- Plugin builds (VST3/CLAP via a Rust plugin framework) in addition to the standalone app.
