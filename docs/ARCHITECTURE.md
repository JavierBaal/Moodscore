# Architecture

> Draft. This describes the intended design; it will change as the prototype teaches us things.

## Design goal

An AI agent should be able to perform a drone piece live, even though every decision it makes takes seconds. The architecture solves this by splitting **intent** (slow, from the agent) from **execution** (fast, in the engine).

### moodscore-dsp

The sound itself, written in Faust (`dsp/*.dsp`) and compiled to Rust at build time. It exposes a flat set of named parameters (cutoffs, levels, detune amounts, effect sends…). It knows nothing about moods, gestures or agents.

Today's graph: six drone voices (`drone_1` … `drone_6`), each two detuned sawtooths with their own slow random pitch drift; `drone_1` also carries a sub sine an octave below. Each voice has its own pitch, level, detune and drift. Each voice's two oscillators open slightly either side of the voice's position (width without delaying either channel); the two voices that sound at rest sit in the centre and the others come in mirrored pairs. The voices are summed with a gentle energy-based normalisation so a full chord grows a few dB rather than slamming the clipper, then go through a stereo Moog-style ladder low-pass, a stereo reverb, a mono-bass crossover (below 150 Hz both channels carry the same signal: the reverb summed with the dry signal would otherwise tip the bass to one side), the master gain and a `tanh` soft clip. Tests check that the image stays centred and that neither channel is delayed. At rest only `drone_1` (A1) and a quiet `drone_2` (E2) sound; the others wait at level 0 on A2, C3, E3, A3.

Faust is used because its standard libraries already provide virtual-analog filters, saturation, oscillators and reverbs, and because Faust code is compact enough to iterate on quickly.

Build integration: a small `build.rs` calls `faust -lang rust` directly (the `faust-build` crate lags behind the compiler; Faust 2.88 changed the shape of its Rust output). Rust code generated by Faust is committed under `crates/moodscore-dsp/generated/`, so the project builds without Faust installed. The build fails if the generated code would take a lock inside `compute()`, which Faust does for lookup tables such as `rdtable` or `os.osc`.

### moodscore-synth

The note voices' synth, in Rust (Faust's per-block parameters can't start a note on its exact sample, and its lookup tables lock). Two morphing oscillators per voice (sine → triangle → saw → square), band-limited with PolyBLEP/PolyBLAMP at the exact sub-sample position, hard sync from a hidden master, unison (width from panning copies, never from delay), FM, sub, noise; a sine wavefolder and a tanh drive with antiderivative antialiasing, both at 2×; a zero-delay-feedback state-variable filter; three ADSRs; two LFOs (tempo-syncable, with delay and fade-in); an eight-slot modulation matrix evaluated every 16 samples. A `Part` plays one patch with up to four voices (stealing the oldest without a click) or one (legato, glide), applies its effects (saturation, chorus, a tempo-synced echo) and writes a dry sound and a reverb send. Events carry their sample offset; the part splits its block there.

A patch is a flat table of numbers (`params.rs`), so the engine smooths it like any other parameter and presets are plain `path → value` files (`presets/`).

### moodscore-ear

Claude's ears: measures audio the way a sound designer listens. Level; spectral centroid over time, tilt, noisiness, energy per band; harmonics against the fundamental (FFT, padded so a harmonic between bins loses < 0.1 dB); envelope (attack, change over a note); pitch with YIN (difference function by FFT) read as held notes, wobble and glides; stereo correlation and balance per band. Works on a part rendered offline (`moodscore_engine::render_part_offline`, a fresh part and optionally a fresh copy of the room, nothing touches the live engine), on the live output (the audio thread hands each chunk to a lock-free queue; the conductor keeps the last 30 s), or on a WAV. Targets compare the headline metrics with tolerances.

### moodscore-engine

Owns the audio callback, the Faust DSP and the two note parts. Its parameters are Faust's followed by `note_1/…` and `note_2/…`. Targets cross from the control thread as one atomic per parameter (last value wins, which is exactly right for targets); counts and choices (`Scale::Discrete`) are taken as they are, never smoothed. Notes cross through a lock-free queue (`rtrb`), each stamped with its frame; the audio thread keeps them in a preallocated list until due. The conductor holds longer phrases in its own agenda, fixed to frames when scheduled (so a phrase keeps its timing) and handed over about 200 ms before each note, so the audio thread only ever holds a few and a stop can still cancel the rest. Every 32 frames the audio thread:

1. Reads the targets.
2. Smooths every parameter toward its target (30 ms time constant; in the log domain for frequencies), so no change reaches the DSP as a step.
3. Runs the note parts (each note on its frame) into four buffers, dry and send, and runs the DSP with them as its inputs.
4. Updates the level meters (peak, 300 ms RMS) for `get_state`. Richer analysis for `listen` comes in Phase 4.

A 1.5 s fade-in avoids a thump when the engine starts.

### moodscore-director

Where musical intent becomes motion.

- **Mood macros.** Six expressive dimensions, each in `0.0–1.0`:
  `tension`, `darkness`, `density`, `motion`, `distance`, `instability`.
  Each macro maps to many DSP parameters through curves defined in data, not code, so they can be tuned by ear without recompiling. A target can name many parameters with a `*` pattern (`drone_*/drift`), and move over only part of the macro's range with a `span` (`density` brings each drone voice in over its own stretch, low to high). Implemented: `darkness`, `instability`, `density` and `distance`; their defaults reproduce the engine's resting sound exactly. `distance` drives the shared room (size, damping, predelay, wet, the direct sound's level and air absorption, and a thinning of the lows for a far sound, applied to drones and notes alike), so the note parts recede with the drones while their own parameters stay untouched.
- **Gestures.** A gesture is a trajectory: a target, a duration, a curve and an optional start offset. Gestures on different parameters run concurrently. A new gesture on a parameter that is already moving starts from wherever that parameter is right now, so changes of mind never cause jumps.
- **Scenes.** Named snapshots of the macro state and selected raw parameters, stored as JSON.

Runs on a control thread at 500 Hz and writes parameter targets to the engine.

Ownership: every parameter is under either macro control or manual control. Under macro control, at most one macro *sets* it (`"mode": "set"`, the default) and any number of macros *add* an offset on top (`"mode": "add"`); the sum is clamped to the parameter's range. With no setter, offsets start from the parameter's default. `gesture` takes a parameter into manual control starting from its current value, and it stays there: a hand-set value is a deliberate choice, so later morphs leave it alone (the state names the macros holding off under `held_from`). A `morph` with `reclaim` takes it back, blending from the manual value to the macros' value over the morph's duration.

The conductor also holds transport fades scheduled with `start_in`, and fires them from the control loop when due.

Harmony (`harmony.rs`) is pure music theory: keys and modes, Roman-numeral chords spelled by letter, and voice leading (each voice takes the chord tone that moves it least, covering the chord and avoiding unisons). The director walks a harmonic plan in its own clock: each chord change is anchored to the moment it was due (not the control tick that noticed it) and played as glides on the voice pitches. Voice pitches have a third owner, `harmony`, alongside macros and manual.

Musical time (`tempo.rs`) is a tempo map: the last tempo change (time, beat position, tempo, an optional ramp along a curve) plus the metre and where bar 1 began. Beats at any instant come from a closed form (each curve's integral is known), and the inverse, the instant a beat falls on, is solved to well under a sample, so nothing is accumulated tick by tick and nothing drifts. Positions are counted in quarter notes inside, so a change of metre never moves the music. Harmony walks its plan step by step: a chord counted in beats or bars ends when the map reaches its last beat, so a tempo change mid-chord reshapes what is left of it. The map is `Copy` and never allocates. Besides the change in force it holds up to eight changes waiting for their beat (stored as quarter-note positions, which never move), so a ritardando from bar 33 or the next section's tempo is known to everything worked out ahead of it: each query is answered by the change in force at that moment. A harmonic plan that waits for a later beat likewise waits behind the plan walking now, and `Director::chord_at` answers from whichever is in force at the time asked.

Sections (`cues.rs`) are a cue list the conductor runs on its own. Each section lasts so many bars (counted in the metre in force when it begins) or seconds; its actions are closures the MCP layer has already validated (every one of them, before the list is accepted, partly on a copy of the director), each with how far ahead it is set up and its turn. When a section begins, the next is measured from the tempo map then and queued; the conductor's loop fires whatever is due each tick, outside every lock, with the moment it lands on (`StartOn::AtQuarter` or `AtTime`). Tempo, harmony, sequences and phrases are set up 0.6 s ahead (more than the half second sequences are worked out ahead), so they land on the downbeat; a patch 50 ms before; moves and fades on the moment. The MCP tools are built the same way: each prepares an action and runs it at once, so a tool called directly and the same tool inside a section share one code path.

Sequences (`sequence.rs`) are pure too. A `Pattern` is a cycle of steps (an arpeggio over the chord sounding, or a motif in degrees that follow the chords or in fixed notes), and a `Runner` turns it into note events at exact times, step by step, asking the director which chord sounds when each step lands (`Director::chord_at` walks a copy of the harmony ahead; a chord landing up to 60 ms late still counts). The conductor runs each part's sequences about half a second ahead and puts their notes in the same agenda as phrases. Everything scheduled ahead is fixed to frames on one line from the director's clock to engine frames, shared by every part, so layers that start on the same bar sound together: the line follows the audio forward at once if it gets ahead (nothing may be late) and resets only if the audio falls well behind (it stalled or restarted). A new sequence on a part stops the old one on its first downbeat and cuts what the old one had already put in the agenda past it. Running ahead in the conductor rather than in the audio thread keeps the sample accuracy (every note has its frame) while the tempo map and the harmony stay in the director; the cost is that a change asked for "now" takes up to half a second to be heard, which changes on the bar never notice.

### moodscore-mcp

The MCP server, built on `rmcp`. It validates tool calls, turns them into director commands and reports state back. See [MCP_TOOLS.md](MCP_TOOLS.md).

### moodscore (binary)

Wires everything together: device selection, config, logging, and later a minimal GUI showing the macros moving so the human can watch, and intervene in, what the agent is doing.

## Real-time rules

The audio thread must never:

- allocate or free memory
- take a lock
- do I/O (files, network, logging)
- wait on another thread

All communication with the audio thread goes through preallocated lock-free queues (`ringbuf` or equivalent). These rules are not negotiable; a drone engine that clicks is useless.

## The latency model

| What | Timescale |
|---|---|
| Agent decides and calls a tool | 1–10 s |
| Director schedules a gesture | < 1 ms |
| Parameter reaches the audio thread | 1 audio block |
| Gesture plays out | seconds to minutes |

Because gestures are long compared with the agent's thinking time, the agent is always *ahead* of the sound, never chasing it. That is the whole point.

## Open questions

- Fixed DSP graph vs. switchable voice types per slot.
- How much the human can override the agent in real time, and how the agent learns about it (likely: the director records human changes and `get_state` reports them).
- Faust static compilation only, or optional JIT hot-reload (LLVM) for live DSP editing later.
- Plugin builds (VST3/CLAP via a Rust plugin framework) in addition to the standalone app.
